# 維度 8：基礎設施與維運韌性

ERP 停機的成本是「全公司停止出貨」。這個維度問三個問題：**出事你會知道嗎？知道了能修嗎？修不了能還原嗎？**

本維度大量項目無法從程式碼確認，**該列「未檢測」就列，並附自查步驟**。

---

## 8.1 備份與復原 — P1（無備份時為 P0）

- 資料庫是否有自動備份，頻率為何
- 備份保留多久，是否有異地／跨雲副本
- 備份是否加密
- **是否實際演練過還原**——沒演練過的備份不算備份
- 能否還原到任意時間點（PITR），或只有每日快照
- 檔案儲存（附件、憑證掃描檔）是否也在備份範圍
- RPO／RTO 是否有共識（能接受掉多少資料、多久內要恢復）

**自查提問**：「如果現在資料庫被誤刪，你能在幾小時內恢復到幾點的狀態？」答不出來就是 P1。

---

## 8.2 資料庫變更管理 — P1

- 是否有 migration 檔且納入版控
- schema 是否曾被手動修改（導致環境間不一致）
- migration 是否可回滾，破壞性變更（drop column）是否有保護
- 正式環境的 migration 是否有審查與備份前置步驟

---

## 8.3 環境隔離 — P0 / P1

紅旗：
- 開發／測試／正式共用同一個資料庫 ← P0
- 測試環境可寄出真實 Email／簡訊給真實客戶
- 測試環境可呼叫正式的金流、發票、EDI
- 本機開發直接連正式 DB
- 正式環境的除錯模式開啟

---

## 8.4 可觀測性 — P1

- 是否有錯誤追蹤服務，且錯誤真的有人看
- 是否有結構化日誌，能依 request id／使用者／租戶追蹤
- 關鍵業務指標是否有監控（訂單建立失敗率、同步失敗、佇列積壓）
- 是否有告警，告警送到哪裡，**是否有人在半夜會看到**
- 日誌保留期限是否足以支援事後調查（建議 ≥90 天）

**紅旗**：整個系統只靠使用者打電話來反映問題。

---

## 8.5 韌性 — P1

- 外部呼叫（金流、發票、LLM、第三方 API）是否有 timeout
- 失敗是否有重試，重試是否冪等（見維度 3.4）
- 外部服務掛掉時系統是否整站白畫面，或能降級運作
- 是否有斷路器避免連鎖失敗
- 佇列與背景工作失敗後是否有 dead letter 與人工處理途徑

---

## 8.6 帳號與存取生命週期 — P1

ERP 的使用者是員工，會來會走。

- 離職員工帳號是否有停用流程（**檢查現有使用者清單中是否有已離職者**）
- 是否有閒置帳號自動停用
- 管理員帳號數量是否過多
- 共用帳號（`admin@company.com` 大家一起用）→ 稽核軌跡失效
- 是否強制 MFA，至少對管理員
- session 有效期、閒置逾時、裝置管理
- 密碼政策與外洩密碼檢查

---

## 8.7 速率限制與濫用防護 — P1

- 登入端點是否有嘗試次數限制（否則可暴力破解）
- 密碼重設、驗證碼寄送是否有頻率限制
- **呼叫付費 API 的端點**（LLM、簡訊、地圖）是否有配額 ← 帳單風險
- 匯出與報表端點是否有頻率限制
- 是否有 WAF 或平台層防護

---

## 8.8 網路與部署面 — P1

- 資料庫是否對公網開放，或限制在私有網段／IP allowlist
- 管理介面（DB adminer、佇列 dashboard、metrics）是否對外可存取
- 安全標頭：HSTS、CSP、`X-Content-Type-Options`、`Referrer-Policy`、`X-Frame-Options`
- TLS 憑證自動續期
- 是否有回滾機制（部署壞了能多快退回）

---

## 8.9 可維護性觀察（影響「未來還修不修得動」） — P2

Vibe coding 專案的長期風險，一併列入本維度評分：

- 是否有一行指令能跑 build／typecheck／test，且真的跑得起來
- 關鍵路徑（登入、建單、審批、結帳）有無自動化測試
- 超過 800 行的檔案數量（AI 修改長檔案的正確率顯著下降）
- `any`／`@ts-ignore` 密度、`strict` 是否開啟
- 同一邏輯的重複實作數量（改一處漏三處的風險）
- 正式路徑上殘留的 `TODO`、mock 資料、寫死的測試 id
- 是否有 `CLAUDE.md`／`AGENTS.md`／README 且內容未過期

---

## 常見誤判，不要報

- 託管平台已預設提供的能力（Vercel 的 TLS、Supabase 的每日備份）——但仍需確認方案層級是否真的包含
- 早期專案尚未導入監控——降級 P2 並註明上線門檻
- 單人專案缺少部署審查流程
