# 維度 6：資料曝光

租戶隔離與授權都對，資料仍可能從側面流出去。ERP 的資料價值高——客戶名單、報價、成本、薪資——**外洩通常不是被駭，是被合法登入的人一次拉走。**

---

## 6.1 API 過度回傳 — P1

紅旗：
- `select *` 或 ORM 預設回傳整列，包含 `password_hash`、`api_token`、`cost`、`salary`、內部備註
- 使用者物件序列化時未過濾（回傳含 email、電話、角色的完整清單）
- 關聯資料被連帶帶出（查訂單時把客戶的所有欄位一起 include）
- 錯誤回應中夾帶原始資料

**檢查方法**：找列表與明細端點的 select／serializer，對照 schema 中的敏感欄位清單。

---

## 6.2 無界查詢與大量下載 — P1

**ERP 資料外洩的主要管道。**

紅旗：
- 列表 API 無分頁，或 `limit` 由 client 指定且無上限（`?limit=999999`）
- 匯出功能無筆數上限、無頻率限制、無稽核紀錄
- 報表 API 可一次撈取全年度資料
- GraphQL 未限制查詢深度與複雜度
- 批次 API 可一次請求數千個 id

**觸發情境**：業務離職前一晚，把全部客戶、報價、成本匯出成 Excel 帶走。系統沒有紀錄，公司事後無法舉證。

**正確做法**：分頁上限（如 100）＋ 匯出速率限制 ＋ 匯出必留稽核 ＋ 大量匯出需主管核准或至少發出通知。

---

## 6.3 錯誤訊息揭露 — P2

紅旗：
- 回傳原始例外訊息、SQL 語句、stack trace 給前端
- DB 約束錯誤直接透出（洩漏表名與欄位名）
- 開發模式錯誤頁在正式環境啟用
- 登入失敗訊息區分「帳號不存在」與「密碼錯誤」→ 可枚舉員工帳號

---

## 6.4 枚舉與旁路推論 — P2

紅旗：
- 流水號主鍵（`/orders/1023`）→ 可推知營運量，且方便 IDOR 掃描
- 存在與否可由回應碼區分（404 vs 403）
- 搜尋 API 可用來確認某客戶是否為本公司客戶
- 回應時間差異可推論資料存在

ERP 建議業務單據對外識別碼使用不可預測值（UUID／nanoid），或至少確保授權嚴密。

---

## 6.5 前端洩漏 — P0 / P1

紅旗：
- `NEXT_PUBLIC_*`／`VITE_*` 前綴掛了不該公開的值（service role key、DB 連線字串、第三方 secret）← P0
- 後端邏輯（定價公式、成本計算、權限規則）被打包進 client bundle
- source map 上傳到正式環境
- 建置時把 `.env` 內容內嵌進靜態檔
- 被註解掉的測試帳號密碼留在前端程式碼
- HTML 註解、`__NEXT_DATA__`／初始 state 中含未過濾的完整資料 ← 常見：頁面只顯示三個欄位，但 hydration payload 含整列

**檢查方法**：檢查建置產物中是否含敏感字串；檢查 SSR 的 props 傳遞是否過濾。

---

## 6.6 儲存與傳輸 — P0

紅旗：
- Storage bucket 設為 public
- 附件 URL 無簽章或簽章期限過長
- 資料庫對公網開放（無 IP 限制）
- 內部 API 走 HTTP
- 未設定 HSTS
- 備份檔存放於可公開存取的位置

---

## 6.7 快取與 CDN — P1

紅旗：
- 含個資的回應被 CDN 快取（缺 `Cache-Control: private, no-store`）
- 登出後上一頁仍可看到資料（缺 `no-store`）
- 共用快取 key 未含使用者或租戶（見維度 1.5）

---

## 6.8 第三方傳輸 — P1

紅旗：
- 分析工具（GA、Hotjar、Clarity）記錄了含個資的頁面內容或 URL 參數
- 錯誤追蹤服務未過濾 request body
- URL query string 中帶身分證、Email、token（會進伺服器日誌、Referer、瀏覽器歷史）
- 客服／聊天工具的腳本能讀取頁面上的敏感資料
- 送往 LLM API 的內容未去識別化

---

## 常見誤判，不要報

- 公開頁面（行銷網站、公開文件）的資料本來就該公開
- 已明確標示為公開 API 的端點
- 開發環境的設定
- 前端可見但無實際價值的識別碼
