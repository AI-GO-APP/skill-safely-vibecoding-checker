# 維度 2：授權、RBAC 與審批流程

AI 產出的授權邏輯有一個壓倒性的失效模式：**前端藏起來，後端沒擋。** 因為 AI 在寫 UI 時很自然會加 `{user.isAdmin && <Button/>}`，但寫 API 時只關心功能會不會動。

---

## 2.1 認證與授權的區分 — P0

「已登入」不等於「有權限」。ERP 的每個使用者都是已登入的。

紅旗：
- 端點只檢查 `session != null` 就放行寫入操作
- 中介層做了認證，但沒有任何一層做授權
- 註解寫著 `// TODO: add permission check`

**檢查方法**：列出所有寫入型端點（POST／PUT／PATCH／DELETE／server action），逐一標記其授權檢查所在行。無法標記的即為發現。

---

## 2.2 預設拒絕 vs 預設允許 — P0

紅旗：
- 中介層用**黑名單**保護路由（`if (path.startsWith('/admin')) checkAuth()`）→ 新增路由必然遺漏
- `matcher` 設定漏掉了 API 路由或新目錄
- 公開路由清單越長越亂，難以確認完整性

**應該長這樣**：預設全部需要授權，明確列舉公開路由。

**檢查方法**：找到中介層／守衛設定，把它的涵蓋範圍與實際路由清單對比，列出未被涵蓋者。

---

## 2.3 IDOR — 物件層級授權 — P0

ERP 中最常見的實際被利用漏洞。

紅旗：
```
const order = await db.order.findUnique({ where: { id: params.id } })
```
只用 id 查，沒有驗證這張單屬於當前使用者／租戶／部門。

必須是：
```
where: { id: params.id, tenant_id: session.tenantId }
```

**特別注意「巢狀資源」**：`/api/orders/{orderId}/items/{itemId}` — 常見錯誤是驗證了 order 歸屬，卻用 itemId 直接查 item 並允許修改，而該 item 可能屬於別張單。

**檢查方法**：grep `findUnique`／`findById`／`.eq('id',` 等模式，逐一確認查詢條件是否含歸屬約束。

---

## 2.4 資料範圍（Data Scope） — P1

ERP 的權限不只是「能不能用這個功能」，還有「能看到多少資料」：本人／本部門／本分公司／全公司。

紅旗：
- 只有角色（role）概念，沒有資料範圍概念
- 業務員可以查詢全公司的訂單與客戶
- 主管的部門範圍寫死在前端篩選器，API 不驗證
- 組織階層（部門樹）的下屬範圍計算只在前端做

---

## 2.5 欄位層級權限 — P1

ERP 特有：同一筆資料，不同角色能看到的欄位不同。

高敏感欄位：**成本、毛利、採購底價、薪資、員工個資、客戶信用額度、供應商付款條件**。

紅旗：
- API 回傳完整資料列，由前端決定顯示哪些欄位（`select *` 直出）
- 明細 API 與列表 API 的欄位過濾不一致
- 匯出／列印／報表繞過了欄位過濾
- GraphQL 未限制可查詢欄位

**觸發情境**：業務員打開瀏覽器開發者工具的 Network 分頁，就能看到每張訂單的成本與毛利。

---

## 2.6 提權路徑 — P0

紅旗：
- 使用者可以透過個人資料更新 API 修改自己的 `role`／`permissions`／`tenant_id`
- 邀請成員的端點可指定任意角色而不驗證邀請者權限
- **Mass assignment**：`await db.user.update({ data: req.body })` — 整包 body 直接進 update
- 首位使用者自動成為 admin 的邏輯可被重複觸發
- 密碼重設／Email 變更流程可被用來接管他人帳號

**檢查方法**：grep `...req.body`、`...body`、`data: body` 等展開模式；檢查 user／member／role 相關的更新端點是否有欄位白名單。

---

## 2.7 審批流程完整性 — P0

ERP 核心。採購、請款、折扣、調薪都靠審批。

紅旗：
- 狀態轉換沒有狀態機約束——可以直接 PATCH `status: 'approved'`
- 審批人與申請人可為同一人（無 segregation of duties）
- 金額門檻（超過 10 萬需經理核准）只在前端判斷
- 審批後單據仍可修改金額／品項，且不需重新審批 ← **經典漏洞**
- 審批動作沒有紀錄「誰在何時以什麼身分核准」
- 代理審批（授權他人代簽）無期限、無紀錄

**觸發情境**：申請人送出 5,000 元的請款單通過審批，接著把金額改成 500,000，狀態仍是「已核准」。

**檢查方法**：找 status 欄位的更新點，確認每一處是否經過狀態機驗證；找核准後的編輯端點，確認是否會重置審批狀態。

---

## 2.8 前後端一致性 — P1

紅旗：
- 前端有權限判斷（`{can('delete') && ...}`），後端對應端點無對應檢查
- 前端與後端各有一份權限定義，可能不同步
- 選單隱藏被當成安全機制

**檢查方法**：把前端出現的權限字串（`can('x')`、`hasRole('y')`）收集起來，逐一到後端找對應檢查。找不到的即為發現。

---

## 2.9 API 金鑰與機器身分 — P1

ERP 常有對外整合：POS、電商、報表工具、EDI。

紅旗：
- API key 沒有綁定租戶與權限範圍
- key 無有效期、無輪替機制、無使用紀錄
- 對外 webhook 的接收端未驗證簽章
- 整合帳號使用了 admin 權限（因為「比較方便」）

---

## 常見誤判，不要報

- 框架層級已強制的檢查（如 route group 的 layout 守衛）——先確認再說
- 只讀取公開主檔（幣別、國別）的端點
- 已被上游中介層涵蓋的路由
- 內部函式（未直接暴露為端點）缺少檢查，若其所有呼叫端都已檢查
