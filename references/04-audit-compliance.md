# 維度 4：稽核軌跡與法遵

ERP 是「有人會來查」的系統：內稽、會計師、客戶的資安問卷、主管機關。**出事時無法回答「誰改的」，本身就是嚴重問題。**

法遵基準以台灣為主：個人資料保護法、商業會計法（帳簿憑證保存）、電子發票相關規範。若專案面向歐盟或有國際客戶，另需考量 GDPR。

---

## 4.1 稽核軌跡存在性 — P1

必須有紀錄的動作：

| 類別 | 動作 |
|---|---|
| 身分 | 登入成功／失敗、登出、密碼變更、MFA 變更 |
| 權限 | 角色指派、權限異動、使用者停用、impersonation |
| 金額 | 單據金額修改、折扣調整、價格表變更、信用額度調整 |
| 流程 | 審批通過／退回、單據作廢、狀態轉換 |
| 資料 | 主檔異動、批次匯入、刪除、**匯出與下載** |
| 系統 | 設定變更、整合金鑰產生與撤銷 |

**匯出與下載最常被漏掉，卻是資料外洩的主要管道。** 離職員工帶走客戶名單，通常就是走匯出功能。

紅旗：完全沒有 audit log 表；或只有 `created_at`／`updated_at` 而不知道是誰改的、改了什麼。

---

## 4.2 稽核紀錄的品質 — P1

一筆合格的稽核紀錄要能回答五個問題：**誰、何時、對什麼、做了什麼、從什麼變成什麼。**

紅旗：
- 只記錄動作名稱，沒有記錄變更前後的值
- 沒有記錄操作者的租戶與角色（事後角色改了就查不出當時權限）
- 沒有記錄來源 IP／User-Agent／session id
- 時間戳用本地時間或無時區資訊
- 批次操作只留一筆總計，無法追到個別資料

---

## 4.3 稽核紀錄的不可竄改性 — P1

紅旗：
- 應用程式使用的 DB 帳號對 audit log 表有 `UPDATE`／`DELETE` 權限
- 稽核紀錄與業務資料在同一交易中寫入，業務回滾時稽核也跟著消失（有時是對的，但「刪除」動作的紀錄不該消失）
- 有「清除日誌」功能且無二次稽核
- 稽核紀錄可被一般管理員從 UI 刪除

**檢查方法**：找 audit 表的 schema 與寫入點，確認是否有 append-only 約束（觸發器阻擋 UPDATE/DELETE，或寫入外部不可變儲存）。

---

## 4.4 日誌中的敏感資料 — P0

紅旗：`console.log` / logger 輸出了完整 request body、完整使用者物件、DB 查詢結果。

絕不可進日誌的內容：
- 密碼、token、API key、session id
- 完整信用卡號、CVV
- 身分證字號、護照號碼（應遮罩為 `A12****789`）
- 銀行帳號全碼
- 薪資明細

**特別注意**：錯誤處理中的 `console.error(err)` 常把整個請求上下文（含 body）吐進日誌，而日誌平台的存取權限通常比資料庫寬鬆。

**檢查方法**：grep `console.log`／`logger.` 的參數，看有沒有直接輸出 `req`、`body`、`user`、`session`、`data`。

---

## 4.5 個資盤點與保護 — P1

ERP 幾乎必然持有個資：員工、客戶聯絡人、供應商窗口。

檢查：
- 是否知道哪些欄位是個資（有無盤點文件或 schema 註記）
- 高敏感欄位（身分證、銀行帳號、健康資訊、薪資）是否加密儲存
- 顯示時是否遮罩，且完整值需額外權限與稽核
- 是否有蒐集告知與同意的機制
- 是否能回應當事人的查詢、更正、刪除請求
- 個資是否流向未預期的第三方（分析工具、LLM API、錯誤追蹤服務）← **AI 功能常把整筆資料送給模型供應商**

**觸發情境**：客服 AI 助理把包含客戶身分證字號的工單內容送到第三方 LLM API，且未告知當事人。

---

## 4.6 測試環境的真實資料 — P1

紅旗：
- 從正式環境複製資料到測試環境而未去識別化
- seed 檔或 fixture 中含真實客戶名稱、電話、身分證
- 開發者本機資料庫是正式資料的副本
- 錯誤追蹤服務（Sentry 等）未設定敏感資料過濾

---

## 4.7 資料保留與備份的法遵面 — P1

- 商業會計法要求會計憑證保存 5 年、帳簿 10 年——系統是否支援長期保存與查詢
- 個資法要求特定目的消失後刪除——是否有保留期限機制
- 備份是否加密、是否有異地副本、**是否演練過還原**
- 備份中的個資是否納入刪除請求的處理範圍

---

## 4.8 電子發票與外部憑證 — P2

若系統開立或接收電子發票：
- 發票號碼區間管理、作廢與折讓流程是否符合規範
- 上傳失敗的重試與對帳機制
- 發票資料的保存與不可竄改
- 加值中心 API 憑證的保管

---

## 常見誤判，不要報

- 開發階段專案（尚未有真實使用者）缺少完整稽核軌跡——降級為 P2 並說明上線前必須補齊
- 使用託管服務（Supabase／Vercel）已提供的平台層日誌，若確實涵蓋該項需求
- 純內部工具、無個資、單一使用者的專案
