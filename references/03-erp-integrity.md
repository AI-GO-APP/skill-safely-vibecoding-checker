# 維度 3：ERP 領域完整性

這個維度不是傳統資安，但在 ERP 造成的損失往往更大——**帳不平、庫存錯、多付款**沒有人會發新聞稿，但公司會賠錢，而且很難回溯。

AI 寫業務邏輯時幾乎不會主動處理併發、精度與交易邊界，因為 happy path 測起來都是對的。

---

## 3.1 金額精度 — P1（可能是 P0，視金額規模）

**紅旗：金額用浮點數。**

- JavaScript `number`、TypeScript `number`、SQL `float`／`double precision`／`real`
- 前端計算金額後傳給後端儲存（而非後端重算）
- 稅額、折扣、匯率換算的取整規則散落在多處且不一致

**正確做法**：DB 用 `numeric/decimal(19,4)`，程式用 decimal 函式庫或整數最小單位（分）。

**觸發情境**：`0.1 + 0.2 = 0.30000000000000004`。一萬張單累積下來對不上帳，會計找不出差額在哪。

**檢查方法**：找 schema 中金額欄位的型別；grep 金額相關的加總與乘算是否直接用原生運算子。

---

## 3.2 交易邊界 — P0

紅旗：多個必須同生共死的寫入沒有包在同一個資料庫交易中。

ERP 典型組合：
- 建立訂單 + 扣減庫存 + 寫入異動明細
- 出貨 + 更新單據狀態 + 產生應收
- 審批通過 + 更新狀態 + 寫稽核紀錄
- 轉帳分錄的借方與貸方

**特別紅旗**：交易中夾雜外部 API 呼叫（寄信、呼叫金流、呼叫 LLM）。外部呼叫慢或失敗會拖垮交易，或造成「交易回滾了但信已經寄出」。外部副作用應該在交易提交後、或透過 outbox 模式處理。

**檢查方法**：找有多個 `create`／`update` 連續出現的 handler，確認是否有 `$transaction`／`BEGIN`／`transaction()` 包覆。

---

## 3.3 併發控制 — P1

紅旗：
- 庫存扣減用「先讀後寫」：`const s = await get(); await set(s.qty - n)` ← 兩個請求同時進來就超賣
- 沒有樂觀鎖（version／updated_at 比對）也沒有悲觀鎖（`SELECT ... FOR UPDATE`）
- 單號產生用「查最大值 +1」← 高併發下必然重號
- 沒有唯一約束保護的業務鍵（單號、料號、統一編號）

**正確做法**：原子更新（`UPDATE ... SET qty = qty - n WHERE qty >= n`）＋ DB 唯一約束＋序列（sequence）產生單號。

**觸發情境**：促銷開賣瞬間，最後一件商品賣出三次。

---

## 3.4 冪等性 — P1

紅旗：
- 送出按鈕沒有防連點，且後端無冪等保護 → 重複建單、重複付款
- 金流／電子發票 webhook 沒有處理重送（外部系統會重送，這是規格不是意外）
- 重試機制（retry）套在有副作用的操作上，而該操作不冪等

**正確做法**：客戶端產生 idempotency key，後端以唯一約束擋重複；webhook 以外部交易 ID 去重。

---

## 3.5 單據狀態機 — P1

紅旗：
- 狀態欄位是自由字串，任何值都能寫入
- 狀態轉換沒有集中定義，散落在各個 handler
- 缺少非法轉換的防護：已作廢 → 已出貨、已關帳 → 編輯

**檢查方法**：找 status 欄位的所有寫入點，看是否收斂到單一轉換函式。

---

## 3.6 刪除語意 — P1

**ERP 原則：業務單據不做實體刪除，用作廢／紅字沖銷。**

紅旗：
- 對已過帳的單據執行 `DELETE`
- 軟刪除欄位（`deleted_at`／`is_deleted`）存在，但查詢沒有一致過濾 → 已刪資料出現在報表
- 軟刪除的資料仍被外鍵引用，導致明細指向不存在的主檔
- 「刪除」實際上是硬刪，但使用者以為可以復原

**觸發情境**：使用者刪掉一張已開發票的訂單，帳務系統對不上，且無法還原。

---

## 3.7 期間關帳與時間 — P1

紅旗：
- 沒有會計期間的概念，任何日期的單據都能新增與修改
- 已關帳期間仍可異動 ← 會計上不可接受
- 單據日期可任意回填（backdating）且無稽核
- 時間戳混用本地時間與 UTC；跨時區的日結邊界未定義
- 用 `new Date()` 取業務日期，而非使用者所在時區的營業日

---

## 3.8 主檔異動的連鎖影響 — P2

紅旗：
- 修改料號的單位／稅率／幣別，會改寫歷史單據的計算結果（歷史單據應保存當時的快照值）
- 客戶／供應商主檔可被硬刪，但仍有歷史交易引用
- 價格表變更沒有生效日期，改了就立即影響所有報價

**原則**：單據上的價格、稅率、單位、匯率應在建立時寫入單據本身（快照），而非每次讀取時 join 主檔。

---

## 3.9 計算一致性 — P2

紅旗：
- 同一個金額（含稅總計、毛利、庫存可用量）有多處各自實作，公式不同
- 前端顯示的合計與後端計算的合計來自不同邏輯
- 報表數字與明細數字對不起來

**檢查方法**：grep 稅／合計／可用量的計算，數一數有幾種實作。超過一種即為發現。

---

## 常見誤判，不要報

- 明確為草稿（draft）階段的單據允許自由編輯與刪除，這是正確設計
- 統計快取與即時數字有落差，若有明確的重算機制
- 非財務性的資料（如系統設定、標籤）使用硬刪除
